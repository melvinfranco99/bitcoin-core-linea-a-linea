Nivel 4 · Lógica de gasto

Script: el lenguaje que bloquea las monedas

Cada moneda lleva un pequeño programa-candado (scriptPubKey). Para gastarla hay que aportar datos (scriptSig o testigo) que, al ejecutarse junto con el candado, terminen en «verdadero». El intérprete que ejecuta esto es uno de los archivos más críticos de Bitcoin: src/script/interpreter.cpp.

Una calculadora de pila

Script es como una calculadora antigua de notación polaca inversa: lee instrucciones de izquierda a derecha; los datos se apilan y los operadores (opcodes) toman elementos de arriba de la pila y dejan el resultado.

Un montón de platos. «2» pone un plato con un 2. «3» pone otro con un 3. «OP_ADD» quita los dos de arriba, los suma y pone un plato con un 5. «5 OP_EQUAL» compara: si los dos de arriba son iguales, deja «verdadero».

Script no tiene bucles a propósito: así cualquier programa termina siempre y su coste es predecible. No es «Turing completo», y eso es una característica de seguridad.

Los límites del lenguaje

Ningún dato apilado puede superar 520 bytes. Como mucho 201 opcodes «de verdad» por script (los de empujar datos no cuentan). Multifirma clásica: hasta 20 claves. Un script no puede pasar de 10 000 bytes. Pila + pila alternativa: máximo 1000 elementos. El umbral entre «altura» y «fecha» para los bloqueos de tiempo (visto en el nivel 3).

El bucle principal: EvalScript

Esta función recorre el script instrucción a instrucción. Es larga (unas 830 líneas) pero muy regular: un gran switch con un case por opcode. Primero, la preparación y la lectura de cada instrucción:

«Falso» es un vector vacío; «verdadero» es el byte 1. Hay tres «sabores» de ejecución: BASE (scripts clásicos), WITNESS_V0 (SegWit) y TAPSCRIPT (Taproot). Algunas reglas cambian según el sabor. pc («program counter») apunta a la instrucción actual. vfExec recuerda, para cada IF abierto, si estamos en una rama que se ejecuta o que se salta. Una segunda pila auxiliar. Primer límite: tamaño del script. ¿Estamos en una rama activa? Sólo si todos los IF abiertos son verdaderos. Lee la siguiente instrucción. Si el script está cortado a mitad de un dato, error. Límite de 520 bytes por elemento. Cuenta opcodes (en scripts no Taproot). Estos opcodes están desactivados desde 2010 (CVE-2010-5137): Satoshi los quitó porque algunos permitían ataques de denegación de servicio (p. ej. OP_CAT o OP_MUL creando datos gigantes). Aparecer en una rama ejecutada o no invalida el script. Si es un dato y estamos en rama activa, se apila (exigiendo la codificación mínima si la bandera MINIMALDATA está activa). Los opcodes sólo se ejecutan en ramas activas… salvo IF/ELSE/ENDIF, que siempre hay que procesar para saber dónde termina cada rama.

Control de flujo: IF / ELSE / ENDIF / VERIFY / RETURN

Si estamos dentro de una rama saltada, el IF no consume nada: sólo apila «falso» para que su rama también se salte. En Tapscript, el valor del IF debe ser exactamente vacío o exactamente 01 (regla de consenso). Evita que alguien cambie la transacción usando otra representación de «verdadero» (maleabilidad). En SegWit v0 esa misma regla es sólo de política (la aplica tu mempool, no el consenso). Convierte el dato a booleano (ver abajo). Recuerda si esta rama se ejecuta. ELSE invierte la rama actual. ENDIF la cierra. VERIFY: si la cima no es verdadera, el script falla en el acto. OP_RETURN hace fallar siempre. Por eso las salidas que empiezan por OP_RETURN son imposibles de gastar y se usan para guardar datos. Cualquier byte distinto de cero hace que sea verdadero… …salvo el «cero negativo»: todo ceros y un 0x80 final (en Script los números usan el bit alto del último byte como signo).

Opcodes de pila y comparación

Casi todos los opcodes empiezan igual: comprobar que hay suficientes elementos. Si no, error (nunca leer memoria que no existe). Copia la cima y la apila. Comparación byte a byte, no numérica. Comentario histórico de Satoshi: no hay OP_NOTEQUAL porque 01 y 0100 son el mismo número pero bytes distintos; un listillo podría aprovecharlo. Deja verdadero o falso… …y la versión VERIFY además exige que sea verdadero.

Opcodes criptográficos

El resultado mide 20 bytes (RIPEMD160, SHA1, HASH160) o 32 (SHA256, HASH256). OP_HASH160 = RIPEMD160(SHA256(x)): lo que se usa en direcciones 1… y bc1q…. Quita el dato original y apila su hash. El penúltimo elemento es la firma… …y la cima, la clave pública. Verifica: comprueba la codificación, calcula qué se firmó (el «sighash», abajo) y llama a libsecp256k1. Si la firma está mal codificada devuelve error; si es simplemente incorrecta, fSuccess = falso. Resultado a la pila. El «scriptCode» es la parte del script que la firma cubre. Rareza histórica: en scripts antiguos se borra la propia firma del scriptCode antes de verificar (una firma no puede firmarse a sí misma). SegWit eliminó esta peculiaridad. Codificación estricta DER (BIP66) y tipo de sighash válido. Aquí se calcula el sighash y se verifica con secp256k1. Si la firma falla, debe estar vacía (si no, se podrían meter firmas basura sin consecuencias = maleabilidad).

El final de EvalScript

Tras cada instrucción, límite de 1000 elementos. Los números de Script están limitados a 4 bytes; si una operación aritmética recibe algo más largo, lanza una excepción que aquí se convierte en error. Un IF sin su ENDIF invalida el script.

¿Qué se firma exactamente? El «sighash»

Una firma no firma «la transacción» tal cual (contiene las propias firmas…), sino un resumen calculado con reglas precisas. El último byte de la firma indica qué partes se cubren:

TipoValorSignifica
SIGHASH_ALL0x01Firmo todas las entradas y todas las salidas (lo normal).
SIGHASH_NONE0x02Firmo las entradas, pero las salidas pueden cambiar («me da igual adónde vaya»).
SIGHASH_SINGLE0x03Firmo sólo la salida con mi mismo índice.
| ANYONECANPAY0x80Sólo firmo mi entrada: otros pueden añadir entradas (útil para colectas).
SIGHASH_DEFAULT0x00Sólo Taproot: equivale a ALL y ahorra un byte.
El famoso bug de SIGHASH_SINGLE en scripts antiguos: si no hay salida con ese índice, se «firma» el número 1. Se mantiene porque cambiarlo sería un hard fork. SegWit v0 (BIP143) rediseñó el cálculo para que fuera lineal (el antiguo era cuadrático: una transacción grande podía tardar minutos en verificarse). Hash de todas las monedas gastadas (salvo ANYONECANPAY). Se calcula una vez y se reutiliza para todas las entradas. Novedad importante: se firma el valor de la moneda gastada. Así una cartera sin conexión (hardware) sabe cuánto está gastando. Hash de las salidas, según el tipo de sighash.

De script a script: VerifyScript

Esta es la función que llama la validación para cada entrada. Junta el desbloqueo y el candado y aplica las reglas especiales de P2SH y SegWit.

programa de testigo?"}

  G -- no --> OK
  W --> OK
Política: el scriptSig sólo debería contener datos, no opcodes. Agujero de julio de 2010: se concatenaban scriptSig y scriptPubKey en un solo script. Con un scriptSig «OP_1 OP_RETURN» (en aquella época OP_RETURN terminaba con éxito) cualquiera podía gastar cualquier moneda. Ahora se ejecutan por separado, compartiendo sólo la pila. Primero el desbloqueo… (se guarda una copia de la pila para P2SH) …después el candado, sobre la pila resultante. Al final, la cima debe ser verdadera. SegWit nativo: el candado es «versión + programa». En SegWit nativo el scriptSig debe estar vacío: todo va en el testigo. P2SH (BIP16): el candado sólo contiene el hash de un script; el que gasta revela el script completo («redeemScript») y se ejecuta. Se recupera la pila tal y como la dejó el scriptSig. El último dato apilado es el redeemScript… …y se ejecuta con el resto de la pila.

SegWit y Taproot: VerifyWitnessProgram

P2WSH: el programa (32 bytes) es el SHA-256 de un script. El último elemento del testigo es el script… …cuyo hash debe coincidir con el programa. P2WPKH: el programa (20 bytes) es un HASH160 de clave. ¡Se fabrica al vuelo el script P2PKH clásico! Por eso P2WPKH se comporta como P2PKH pero con la firma en el testigo. Taproot (versión 1, 32 bytes): el programa es una clave pública «retocada». El «anexo» (byte 0x50): reservado para el futuro. Gasto por clave: un único elemento, una firma Schnorr. Es lo más común y más privado: nadie ve si había scripts alternativos. Gasto por script: se revela un script concreto y un «bloque de control» con la prueba de Merkle de que ese script estaba comprometido en la clave. Comprueba esa prueba: clave interna + camino de Merkle → debe dar exactamente el programa. Ejecuta el script con las reglas de Tapscript (BIP342). Versiones de hoja desconocidas: éxito. Reservadas para futuros soft forks. Versiones de testigo 2–16 desconocidas: cualquiera puede gastarlas según las reglas actuales. Así un futuro soft fork puede darles significado sin romper nodos antiguos (nivel 10).
