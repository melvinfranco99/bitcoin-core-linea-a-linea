No confíes: verifica el código tú mismo

Antes de leer una sola línea hay que asegurarse de que lees el código auténtico, el mismo que acaba convertido en el programa que ejecutas. Este nivel te enseña la cadena de confianza completa, cómo compilar y cómo orientarte en el repositorio.

La cadena de confianza

Cuando instalas un nodo hay varios eslabones entre «lo que escribieron los desarrolladores» y «lo que corre en tu ordenador». Cualquiera de ellos podría ser atacado. La idea es poder comprobar cada uno sin depender de una sola persona.

desde el código"]
  G --> I(("Tu nodo"))
  H --> I
Es como una receta familiar: varios cocineros (los constructores Guix) siguen la misma receta (el código) en sus cocinas y todos obtienen exactamente el mismo pastel, gramo a gramo. Si tu pastel pesa lo mismo que el de diez cocineros independientes, es muy difícil que alguien haya cambiado un ingrediente.

Opción A: obtener y comprobar el código fuente

  1. Clona el repositorio oficial. 
    git clone https://github.com/bitcoin/bitcoin.git
cd bitcoin
git checkout v31.1        # la versión que explica esta web
git rev-parse HEAD           # debe dar 9be056a8a72b624dae9623b2f7bded92c2a21c91
  2. Comprueba la firma de la etiqueta. Cada versión la firma un mantenedor con su clave PGP. Necesitas importar antes su clave pública (búscala en varias fuentes independientes: web personal, servidores de claves, charlas grabadas…). 
    git tag -v v31.1           # "Good signature from …"
  3. (Avanzado) Comprueba toda la historia de fusiones. El script contrib/verify-commits/verify-commits.py verifica que cada commit de fusión está firmado por una de las claves de trusted-keys. Ojo, el propio README advierte: «no puedes usar un script no confiable para verificarse a sí mismo». Usa una copia del script que ya hayas verificado antes.

Opción B: verificar los binarios publicados

Si prefieres descargar el programa ya compilado desde bitcoincore.org, descarga también SHA256SUMS y SHA256SUMS.asc:

# 1. ¿El archivo descargado tiene el hash que aparece en la lista?
sha256sum --ignore-missing --check SHA256SUMS
# 2. ¿La lista está firmada por constructores en quienes confío?
gpg --verify SHA256SUMS.asc
# 3. O todo junto con el script del propio repositorio:
./contrib/verify-binaries/verify.py pub v31.1

Las claves de los constructores están en el repositorio bitcoin-core/guix.sigs (carpeta builder-keys/). Tú decides cuántas firmas independientes te bastan.

Opción C (la mejor): compilación reproducible

El sistema contrib/guix compila Bitcoin Core dentro de un entorno totalmente controlado (GNU Guix) partiendo de un compilador mínimo, de forma que cualquiera obtiene binarios idénticos bit a bit. Los constructores publican los hashes de lo que obtuvieron (guix-attest) y cualquiera puede compararlos (guix-verify). Si tú también compilas con Guix y te sale el mismo hash, has cerrado el círculo: el binario oficial sale exactamente de este código.

Compilar para leer y experimentar

Para estudiar no hace falta Guix; basta con CMake (instrucciones completas en doc/build-unix.md):

# Debian/Ubuntu: dependencias mínimas
sudo apt-get install build-essential cmake pkgconf python3 libevent-dev libboost-dev
cmake -B build
cmake --build build -j"$(nproc)"
ctest --test-dir build          # ejecuta las pruebas unitarias
./build/bin/bitcoind -regtest   # un nodo en una red privada de pruebas
Consejo para aprender

Arranca un nodo en -regtest: es una red privada donde tú minas bloques al instante (bitcoin-cli -regtest generatetoaddress 1 <dirección>). Así puedes poner puntos de ruptura con gdb en cualquier función de esta web y ver cómo se ejecuta.

Así arranca todo: main()

El programa bitcoind empieza aquí. Fíjate en que es corto: casi todo el trabajo lo delega.

Para leer C++ sin saber C++

Bitcoin Core está escrito en C++. No necesitas dominarlo; con esta chuleta podrás seguir el 90 % del código.

Ves estoSignifica
// texto o /* texto */Comentario: el compilador lo ignora. ¡Léelos! Explican el porqué.
int64_t x = 5;Variable x, entero de 64 bits con signo. uint32_t = entero de 32 bits sin signo (nunca negativo).
class CTxOut { … };Define un tipo de objeto con datos (campos) y funciones (métodos). La «C» inicial es una costumbre antigua: «Class».
std::vector<CTxIn> vin;Una lista de longitud variable de objetos CTxIn.
const CBlock& blockRecibe el bloque «por referencia» (sin copiarlo) y promete no modificarlo (const).
CBlockIndex* pindexUn puntero: la dirección de memoria donde está el objeto. pindex->nHeight lee su campo.
nullptrPuntero que no apunta a nada.
A::BB dentro del espacio de nombres o clase A. Ej.: Consensus::CheckTxInputs.
return state.Invalid(…, "bad-…")Patrón típico: marca algo como inválido con un motivo y sale de la función devolviendo false.
assert(x);Si x es falso, el programa se detiene en el acto. Se usa para cosas que «no pueden pasar».
a >> n, a << n, &, |, ^Operaciones de bits: desplazar a la derecha (dividir por 2ⁿ), a la izquierda (multiplicar), Y, O, O-exclusivo.
template<typename T>Función o clase «genérica» que sirve para varios tipos.
EXCLUSIVE_LOCKS_REQUIRED(cs_main)Anotación: para llamar a esta función hay que tener cogido el candado cs_main (para que dos hilos no toquen lo mismo a la vez).
LOCK(cs_main);Coge ese candado hasta el final del bloque { }.
auto x{f()};Variable cuyo tipo deduce el compilador. Las llaves {} son otra forma de inicializar.
std::optional<T>Un valor que puede estar o no estar.

Cómo usar esta web junto a tu copia del código

  1. Ten abierta tu copia (git checkout v31.1) en un editor.
  2. En cada fragmento de esta web verás el archivo y las líneas exactas (p. ej. src/pow.cpp · líneas 50–85). Ábrelas en tu editor y compara.
  3. Si quieres comprobar que esta web no se ha inventado nada, ejecuta su generador: descarga el proyecto, ejecuta python3 build.py y fallará si algún fragmento citado no existe exactamente en ese commit.
